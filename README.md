# Бэклог

Локальная галерея личного бэклога игр, сериалов, кино и аниме. Статический сайт — просто откройте `index.html` в браузере.

## Как это устроено

- `data.js` — базовый каталог тайтлов (редактируется вручную/через Claude).
- Статус просмотра, личная оценка, удаление и быстро добавленные черновики редактируются прямо в интерфейсе и хранятся в `localStorage` вашего браузера поверх `data.js` — четыре ключа:
  - `backlog-overrides` — правки полей тайтла по id: статус, оценка и (с Task 39) любое другое поле карточки, отредактированное через «Редактировать» в модалке;
  - `backlog-deleted` — id удалённых тайтлов из `data.js` (черновики сюда не попадают — они просто удаляются из `backlog-added`);
  - `backlog-added` — черновики, добавленные через форму быстрого добавления;
  - `backlog-parts` — отмеченные сезоны/части по id тайтла (`{ "the-boys-2019": [0, 1, 2] }` — индексы в массиве `parts`).
- Эти четыре ключа синхронизируются между устройствами через Supabase — см. «Синхронизация» ниже. Рядом с ними лежат два служебных ключа: `backlog-sync-seeded` (какие таблицы этот браузер уже сверил с общим состоянием) и `backlog-sync-outbox` (правки, которые не удалось отправить — например, сделанные офлайн).
- Чтобы сбросить все локальные правки и вернуться к состоянию `data.js` "as is", очистите все ключи в localStorage (DevTools → Application → Local Storage), либо в консоли браузера: `localStorage.removeItem('backlog-overrides'); localStorage.removeItem('backlog-deleted'); localStorage.removeItem('backlog-added'); localStorage.removeItem('backlog-parts'); localStorage.removeItem('backlog-sync-seeded');`. Учтите: при следующей загрузке они наполнятся заново из Supabase — чтобы сбросить по-настоящему, чистите и таблицы в Supabase.

## Синхронизация

Каталог (`data.js`) — статика, он одинаков у всех и правится только через Claude. А вот слой правок поверх него (статусы, оценки, удаления, черновики, отмеченные сезоны) — личный и общий на двоих, поэтому он живёт в Supabase и приезжает на все устройства.

**Как это устроено.** `lib/storage.js` не тронут и ничего не знает про сеть: он по-прежнему читает и пишет те же четыре ключа `localStorage`. Всё остальное делает `lib/sync.js`, который относится к `localStorage` как к локальному зеркалу общего состояния:

- **при загрузке** — `pullState()` тянет четыре таблицы и раскладывает их ровно в те же четыре ключа, после чего обычный старт приложения работает как раньше;
- **при каждой правке** — сначала пишется `localStorage` (интерфейс обновляется мгновенно и работает офлайн), следом та же правка уходит в Supabase;
- **при чужой правке** — realtime-подписка будит вкладку, она перечитывает состояние и перерисовывается сама, без перезагрузки.

Одна таблица на один ключ:

| Таблица | Ключ | Что внутри |
| --- | --- | --- |
| `overrides` | `backlog-overrides` | статус, оценка и любые отредактированные поля карточки по id |
| `deleted_titles` | `backlog-deleted` | id удалённых каталожных тайтлов |
| `drafts` | `backlog-added` | черновики быстрого добавления |
| `parts` | `backlog-parts` | отмеченные сезоны/части |

**Сначала рисуем, потом синхронизируем.** Клиент Supabase (единственная внешняя зависимость проекта, подключается через CDN с `defer`) грузится уже после первой отрисовки. Если он не загрузился, если сеть отвалилась или Supabase недоступен — приложение работает целиком на `localStorage`, ровно как до появления синхронизации: в консоли будет предупреждение, на экране ничего не сломается. Это же держит офлайн-режим PWA (`sw.js`) осмысленным.

**Правки, сделанные офлайн, не теряются.** Если отправить изменение не удалось, оно запоминается в `backlog-sync-outbox` и уходит наверх при следующем выходе в сеть — по событию `online` или при следующей загрузке. Очередь всегда разбирается **до** чтения общего состояния: иначе Supabase, который про эти правки ещё не знает, стал бы источником истины и затёр бы их. Порядок здесь и есть вся защита.

**Чужая правка никогда не перебивает вашу работу.** Если открыта модалка, панель жанров или курсор/фокус в сетке — новые данные молча уезжают в `localStorage`, а перерисовка откладывается до момента, когда вы выйдете из сетки или закроете панель (тот же механизм отложенного пересорта, что и у быстрых кнопок статуса).

**Ключ намеренно лежит в исходниках.** `anon`/publishable-ключ — это не секрет, а публичный идентификатор проекта: его обязан предъявить любой браузер, чтобы вообще достучаться до базы. Данные защищены RLS-политиками на таблицах и тем, что адрес проекта никто посторонний не знает. Прятать его в статическом сайте всё равно негде. Та же логика — у `TMDB_KEY`/`RAWG_KEY` в `app.js` (см. «Автозаполнение при быстром добавлении» ниже): это клиентские ключи, которые TMDb/RAWG сами ожидают увидеть прямо из браузера, а не серверные секреты.

**Первый запуск.** Браузер, который до этого копил правки только у себя, при первом запуске сначала отправляет своё состояние наверх и только потом тянет общее — иначе пустая база ответила бы «у тебя ничего нет» и стёрла бы всю историю. Отметка о том, что это уже сделано, лежит в `backlog-sync-seeded` (по таблицам).

### SQL схемы

```sql
create table if not exists overrides (
  id text primary key,
  status text,
  rating int,
  updated_at timestamptz not null default now()
);

create table if not exists deleted_titles (
  id text primary key,
  deleted_at timestamptz not null default now()
);

create table if not exists drafts (
  id text primary key,
  title text not null,
  category text not null,
  status text not null default 'queue',
  airing_status text,
  year int,
  genres jsonb not null default '[]'::jsonb,
  rating int,
  synopsis text not null default '',
  cover text not null,
  draft boolean not null default true,
  created_at timestamptz not null default now()
);

-- Отмеченные сезоны/части. Добавлена позже трёх остальных: без неё
-- статусы сериалов и аниме с чеклистом не синхронизируются (на втором
-- устройстве пустой чеклист вычислит «В бэклоге» и перебьёт приехавший статус).
create table if not exists parts (
  id text primary key,
  indices jsonb not null default '[]'::jsonb,
  updated_at timestamptz not null default now()
);

alter table overrides enable row level security;
alter table deleted_titles enable row level security;
alter table drafts enable row level security;
alter table parts enable row level security;

create policy "allow all - overrides" on overrides for all using (true) with check (true);
create policy "allow all - deleted_titles" on deleted_titles for all using (true) with check (true);
create policy "allow all - drafts" on drafts for all using (true) with check (true);
create policy "allow all - parts" on parts for all using (true) with check (true);

alter publication supabase_realtime add table overrides;
alter publication supabase_realtime add table deleted_titles;
alter publication supabase_realtime add table drafts;
alter publication supabase_realtime add table parts;
```

Если таблицы `parts` ещё нет, приложение работает и без неё: чеклист сезонов остаётся локальным, в консоли появляется предупреждение, остальные три таблицы синхронизируются как обычно. Как только таблицу создадите — накопленный локально `backlog-parts` уедет наверх при следующей загрузке сам.

**Миграция (Task 39: редактирование карточек в интерфейсе).** До этой задачи `overrides` нёс только `status`/`rating`. Теперь через модалку можно править любое поле карточки, и `overrides` должен уметь их хранить — выполните в SQL-редакторе Supabase (аддитивно, существующие колонки и политики не трогает):

```sql
alter table overrides
  add column if not exists title text,
  add column if not exists category text,
  add column if not exists year int,
  add column if not exists genres jsonb,
  add column if not exists synopsis text,
  add column if not exists cover text,
  add column if not exists original_title text,
  add column if not exists season_info text,
  add column if not exists platforms jsonb,
  add column if not exists parts jsonb;
```

Без этой миграции редактирование карточек всё равно работает: правка сохраняется локально в `backlog-overrides` и переживает перезагрузку, push в Supabase падает (в консоли `pushOverride ... failed`), правка ждёт своей очереди в `backlog-sync-outbox` и уедет наверх, как только колонка появится. На другое устройство до этого момента она не попадает.

Это верно начиная с Task 45 — раньше было не так. `applyState` перезаписывал ключ `backlog-overrides` целиком тем, что вернул pull, а pull по таблице без колонки возвращает патч без этого поля вовсе (`shapeOverrides` намеренно не кладёт в патч поле, которого в строке нет). Одного обновления страницы хватало, чтобы только что сделанная правка молча откатилась — на том же устройстве, без всякой синхронизации. Теперь `backlog-overrides` не перезаписывается, а сливается: поле, которое удалённая сторона реально прислала, выигрывает как и раньше, а поле, которого в патче нет, оставляет локальное значение в покое. Остальные три ключа — списки и карты целиком, они по-прежнему перезаписываются.

**После миграции `null` в новой колонке — не правка.** `add column if not exists` проставляет каждой уже существующей строке `overrides` настоящий SQL `NULL` в каждую новую колонку, и PostgREST возвращает именно `null`, а не «поля нет». Пока `shapeOverrides` считал «поле есть, пусть и null» настоящим оверрайдом, сразу после миграции все строки, написанные до неё, начинали присылать `title: null`, `cover: null` и так далее — `applyOverlay` затирал этим реальные значения из `data.js`, и на карточках появлялся буквальный текст «null» и пустые обложки. Теперь `null` для всех этих полей отбрасывается наравне с отсутствующим значением: приложение никогда их так не пишет (пустой текст — `''`, пустой список — `[]`, `draft` — всегда boolean), значит `null` может быть только следом миграции. Исключение — `rating`: `null` там означает «оценка снята», это настоящая правка, и она по-прежнему доезжает. Цена — очистка поля «Год» (единственное поле формы, которое пишет настоящий `null`): локально она сохраняется, но на другое устройство не уезжает. Чинится само: первый же pull после этой правки перестаёт присылать испорченные поля, локальное зеркало очищается на следующей загрузке, а `NULL`-ы в Postgres становятся навсегда безвредными.

**Миграция (Task 43: ручное снятие «черновика»).** Новое поле формы редактирования — тоже просто ещё одна колонка `overrides`, аддитивно:

```sql
alter table overrides
  add column if not exists draft boolean;
```

Та же деградация, что и выше: без колонки чекбокс всё равно снимает бейдж локально и это переживает перезагрузку (в консоли будет `pushOverride ... failed`, правка уйдёт в `backlog-sync-outbox` и повторится позже) — просто не синхронизируется на другое устройство, пока колонка не появится. Именно на этом поле баг из Task 45 и проявился в живую: снять «Черновик», обновить страницу — и бейдж возвращался. У этой колонки была и вторая, независимая причина того же симптома: `draft` отсутствовал в списке полей, которые `shapeOverrides` читает обратно, то есть колонка была «только на запись» — снятая галочка доезжала до Supabase и терялась на обратном пути. Теперь `draft` в списке, и правка возвращается на оба устройства.

## Как добавить новый тайтл

Просто попросите Claude добавить тайтл по названию — он найдёт год/жанры/синопсис/постер, скачает постер в `images/covers/`, допишет объект в `data.js` по схеме ниже и проверит каталог через `node tools/validate-data.js`.

Схема одного тайтла (см. `lib/validate.js` для точных правил):

```js
{
  id: "slug-year",                              // lib/slug.js makeId(title, year)
  title: "Название",
  category: "game" | "series" | "movie" | "anime",
  status: "queue" | "in_progress" | "done" | "unreleased",  // "unreleased" — ставится чекбоксом в форме редактирования (см. ниже)
  airingStatus: "ongoing" | "completed" | null,  // null для game/movie
  year: 2024,
  genres: ["жанр1", "жанр2"],
  rating: null,                                   // 1-10 или null, задаётся пользователем в UI
  synopsis: "Краткое описание.",
  cover: "images/covers/slug-year.jpg",
  originalTitle: "Snatch",                                  // опционально, оригинальное название; показывается только в модалке
  seasonInfo: "Вышло 2 сезона, 3-й анонсирован на 2026.",  // опционально, только для series/anime, не валидируется
  platforms: ["PC", "PS5"],                                 // опционально, только для game, не валидируется
  parts: [                                                  // опционально, только для series/anime, не валидируется
    { name: "Сезон 1", year: 2019, released: true },
    { name: "Сезон 2", year: 2027, released: false }
  ]
}
```

### Сезоны и части

Если у сериала/аниме заполнен `parts`, в модалке вместо трёх кнопок статуса появляется чеклист сезонов, фильмов и OVA в порядке выхода, а статус становится **вычисляемым**:

- ничего не отмечено → «В бэклоге»;
- отмечено что-то → «В процессе»;
- отмечено всё вышедшее **и в списке нет невышедших частей** → «Завершено».

Ключевое правило: пока в списке есть часть с `released: false`, тайтл не может стать «Завершено», даже если всё вышедшее отмечено. Иначе теряется сигнал «я всё посмотрел и жду продолжения» — ради него чеклист и сделан. Невышедшие части рисуются в списке, но их нельзя отметить.

Статус здесь **вычисляется при чтении**, а не хранится: `applyOverlay` подставляет его в тайтл на лету, поэтому карточка, модалка, фильтры, сортировка и счётчики видят одно и то же значение без единой записи. Просто открыть модалку — действие только на просмотр, оно ничего не сохраняет. В `backlog-overrides` статус пишется ровно в один момент: когда пользователь сам ставит или снимает галочку.

Из этого следует важное: ручной статус, выставленный до появления `parts`, **не стирается** — он остаётся в `backlog-overrides` под вычисленным значением. Если `parts` у тайтла убрать, вернётся именно он. У тайтла без `parts` всё остаётся как раньше: обычные три кнопки статуса.

### Редактирование карточек

Кнопка «Редактировать» в модалке открывает форму со всеми полями карточки: название, оригинальное название, категория, год, жанры (через запятую), обложка (URL или путь), синопсис, а для сериалов/аниме — описание сезонов и список частей (название/год/вышло, добавление и удаление строк), для игр — платформы (через запятую). Оценка сюда не входит — она по-прежнему правится звёздами рядом. Статус в общем случае тоже — он правится тремя кнопками статуса, которые остаются рабочими прямо над этой формой, пока она открыта; единственное исключение — чекбокс «Ещё не вышло» (см. ниже).

Поля предзаполняются текущим эффективным значением (`data.js` + уже применённый оверрайд). При сохранении в `backlog-overrides` попадают **только изменившиеся поля** — если ничего не тронуть, оверрайд не запишется вовсе, ровно как и раньше. Ввод грубо проверяется по тем же правилам, что и `lib/validate.js` (категория из списка, год — число или пусто, жанры — список), но неполнота не считается ошибкой: пустой синопсис или отсутствующий год допустимы, как и у черновиков быстрого добавления.

Смена категории саму по себе не трогает `airingStatus` — это поле в форму редактирования не входит, так что, например, при переключении «Кино» → «Сериал» статус выхода придётся поправить отдельно (пока только через Claude/`data.js`).

**Загрузка обложки с устройства (Task 41).** Рядом с текстовым полем URL у поля «Обложка» есть файловый инпут и превью. Выбранный файл читается на клиенте (`FileReader`), уменьшается на `<canvas>` до не более 900px по длинной стороне (апскейл никогда не применяется — файл меньше лимита остаётся как есть) и перекодируется в JPEG (`toDataURL('image/jpeg', 0.82)`); результат — обычная `data:image/jpeg;base64,...` строка — пишется прямо в то же текстовое поле URL и участвует в том же диффе/сохранении, что и обычная ссылка. Отдельного хранилища для картинок нет: `cover` как было, так и остаётся произвольным текстом в `backlog-overrides`/колонке `overrides.cover`. Два поля не мешают друг другу — побеждает то, которое трогали последним. Не-изображение или файл, который не удалось декодировать, показывает короткое сообщение под полями и не ломает форму.

`ponytail:` большие фотографии превращаются в base64-текст прямо в `overrides.cover` без выделенного объектного хранилища или CDN — это нормально для нынешнего масштаба (2 человека, редкие ручные правки), но если такие обложки станут обычным делом и раздуют payload синхронизации или размер строки в Postgres, следующий шаг — bucket в Supabase Storage (загружать файл туда, а в `cover` класть получившийся публичный URL вместо самой data-URI — схему менять не придётся, `cover` и так просто текст).

**Ручное снятие пометки «черновик» (Task 43).** В форме редактирования есть чекбокс «Черновик (требует проверки)», предзаполненный текущим значением `draft` (для обычных записей каталога, у которых поля `draft` вообще нет, — снят). Это обычное поле формы: идёт через тот же список `EDIT_FIELDS`, тот же дифф со снапшотом и тот же `setOverride`/`pushOverride`, что и остальные поля, — отдельного пути записи нет. Сняв галочку у автозаполненного или дописанного вручную черновика и сохранив форму, владелец убирает бейдж «Черновик» с карточки, ничего больше не трогая. В тулбаре рядом со «Скрыть завершённое» есть симметричный фильтр «Только черновики» (`state.draftsOnly`) — чисто клиентская фильтрация по тому же проходу, без изменений в `lib/query.js`/`lib/storage.js`.

**Четвёртый статус «Ещё не вышло» (Task 44).** Для тайтла, который уже занесён в бэклог, но ещё физически не вышел (в кино/цифре/релизе игры), «В бэклоге» вводит в заблуждение — звучит как «доступно, просто не начато», а на деле смотреть/играть пока попросту не во что. Это настоящий статус (`status: "unreleased"`), а не отдельный флаг, но он намеренно не входит в тройку кнопок быстрого статуса на карточке и в модалке — отметить «В процессе» то, что ещё не вышло, не должно быть на расстоянии одного клика. Ставится и снимается чекбоксом «Ещё не вышло» в форме редактирования — он виден для любой категории (кино/сериалы/аниме/игры), кроме случая, когда у тайтла есть чеклист частей (тайтлы с `parts` уже выражают «ещё не вышло» на уровне конкретной части через её `released: false`, см. раздел «Сезоны и части» выше — там чекбокс скрыт, чтобы не конкурировать с чеклистом). Технически `unreleased` — не настоящее поле тайтла: чекбокс участвует в том же дифф-снапшоте `EDIT_FIELDS`, что и остальные поля формы, но при сохранении транслируется в патч `status` (галочка поставлена → `status: "unreleased"`, снята после того как была установлена → `status: "queue"`, самое безопасное значение по умолчанию — восстановить прежний статус ведь неоткуда). Нетронутый чекбокс diff не создаёт вовсе, поэтому он никогда не перезаписывает то, что тем временем сделали три кнопки статуса, которые остаются рабочими прямо над формой, пока она открыта. Отдельной миграции Supabase не нужно: колонка `overrides.status` уже существует, меняется только набор допустимых в неё значений.

### Как устроены id

Есть ровно две конвенции, и они намеренно разные:

- **Каталог `data.js`** — `slug-year` (`dune-3-2026`), т.е. `BacklogSlug.makeId(title, year)`. Так выглядят все записи в каталоге.
- **Черновики быстрого добавления** — голый слаг без года (`dune-3`), потому что в форме быстрого добавления нет поля года. Генерируются через `BacklogSlug.uniqueId(name, existingIds)`, который при коллизии добавляет числовой суффикс (`dune-3`, `dune-3-2`, …).

Черновик считается «перекрытым» каталогом (`BacklogStorage.isSupersededBy` в `lib/storage.js`), если id каталожной записи либо точно равен id черновика, либо равен ему плюс суффикс из четырёх цифр — года. Поэтому черновик `dune-3` исчезает, когда в `data.js` появляется `dune-3-2026`, но не исчезает из-за не связанного с ним `dune-3000-2020`.

### Быстрое добавление

Также можно быстро добавить тайтл прямо в интерфейсе (только название + категория) — он появится как «черновик» с плейсхолдером, а полные данные (жанры/год/постер/описание/seasonInfo) вы допишете тем же способом, попросив Claude, когда будете готовы — черновик автоматически исчезнет, как только в `data.js` появится тайтл с соответствующим id (см. правило выше).

### Автозаполнение при быстром добавлении

Поиск во внешнем источнике запускается сам, без отдельной кнопки: начните печатать название (от 2 символов) в форме быстрого добавления — результаты появляются live, с debounce ~350мс, и обновляются заново сразу при смене категории (категория по-прежнему определяет источник и обязательна для сохранения черновика). Источник выбирается по категории — кино/сериалы через TMDb, игры через **Steam** (с откатом на RAWG — подробности ниже), аниме через **Shikimori** (`shikimori.io`, без ключа, но API требует описательный `User-Agent` — задан константой рядом с остальными поисковыми функциями в `lib/enrich.js`; используется именно `.io`, а не более известный `shikimori.one` — тот отдаёт 301 на `.io` без CORS-заголовков на самом редиректе, из-за чего браузерный `fetch` падает с ошибкой CORS даже при рабочем финальном ответе) — и показывает до 5 подходящих карточек (постер, название, год). Выбор карточки сразу создаёт черновик (`BacklogStorage.addTitle`) с уже заполненными полями (год/жанры/синопсис/обложка, платформы для игр) вместо пустого плейсхолдера — как и обычный черновик, он остаётся `draft: true` и полностью доступен для правки через «Редактировать» после сохранения. Для TMDb и RAWG нужны бесплатные ключи `TMDB_KEY`/`RAWG_KEY`, заданные константами рядом с `SUPABASE_URL` в `app.js`; без ключа, без сети или пока запрос не набрал 2 символа панель результатов просто не показывается (или показывает короткое сообщение вроде «не удалось найти»/«добавь ключ…») и ничего не сломает — ручной ввод и обычная кнопка «+ Добавить» продолжают работать как раньше. В отличие от прежнего источника (Jikan, только английские/ромадзи названия), Shikimori отдаёт уже русские название и описание, так что аниме-черновик из автозаполнения так же полон, как и черновик из TMDb/RAWG.

Для игр сначала пробуется **Steam** — у его официального магазина есть настоящие русские жанры и описания для любого тайтла со страницей в Steam, что заметно лучше англоязычного RAWG. Если Steam ничего не нашёл (не вышедший там тайтл, консольный эксклюзив, пустой/битый запрос — расценивается одинаково, без отдельных сообщений об ошибке), поиск прозрачно откатывается на RAWG, как и раньше. У Steam Storefront API нет CORS-заголовков (прямой `fetch` из браузера падает), поэтому оба его запроса (`storesearch`, `appdetails`) идут через публичный CORS-релей **`proxy.cors.sh`** — работает без ключа, но это стороннее бесплатное API вне контроля проекта, которое может начать требовать ключ или лечь без предупреждения; базовый URL релея вынесен в единственную константу `CORS_PROXY` рядом с `TMDB_KEY`/`RAWG_KEY` в `app.js` — замена на другой релей (или на прямой CORS, если Valve его когда-нибудь добавит) делается правкой этой одной строки. Поскольку Steam отдаёт только флаги Windows/Mac/Linux, а не консольные платформы, выбор Steam-варианта карточки дополнительно делает фоновый поиск по RAWG (по названию из Steam) специально за списком `platforms` — если RAWG что-то нашёл, платформы берутся оттуда, иначе остаются Steam-флаги; эта фоновая RAWG-подгрузка не может провалить выбор карточки — в худшем случае она просто ничего не добавит. RAWG-вариант (когда Steam не нашёл ничего) выглядит и работает точно как раньше — год/жанры/описание/платформы целиком из RAWG.

**Это ускоритель, а не замена ручной проверки** — как и рукописный ввод, результат автозаполнения стоит перепроверить (франшизы, издания, точность жанров) тем же способом, что и любой другой черновик: глазами владельца или Claude.

## Тесты

`lib/` — чистая логика (слаги, фильтры/сортировка, localStorage-оверлей, валидация, синхронизация) — покрыта тестами на встроенном тест-раннере Node (без установки зависимостей). `lib/sync.js` тестируется против поддельного клиента Supabase — обычного объекта с методами `from().select()/.upsert()/.delete()` — так же, как оверлей тестируется против поддельного `localStorage`: ни сети, ни моков SDK.

```bash
node --test tests/*.test.js
node tools/validate-data.js
```

(Note: the bare `node --test tests/` without a glob fails with `MODULE_NOT_FOUND` on this machine's Node version when run from this path — always use the `tests/*.test.js` glob form.)
