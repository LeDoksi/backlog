## 1. Контекст и цель

Бэклог — PWA для личного бэклога игр, сериалов, кино и аниме. Сейчас им пользуются 4 человека в трёх пространствах (общее на двоих с 213 тайтлами и два личных с 7 и 28 тайтлами). Стек сейчас: ванильный JS без сборки (`app.js` на 2800 строк, треть — комментарии), `lib/` с чистой логикой и 227 тестами, Supabase (auth через Google, 6 таблиц, RLS), GitHub Pages.

Владелец хочет три вещи сразу:
1. **Полный редизайн (BL-27):** «удобно и красиво», анимации, кнопки, раскладка, чистка мёртвого кода. В первую очередь телефон, но ПК не забыт.
2. **Личная и общая доска (BL-24):** у каждого одна личная доска и максимум одна общая, между ними переключение.
3. **Социальщина для узкого круга (BL-21):** профиль, друзья, лента, совпадения, глобальный лидерборд, совпадение вкусов и гибкая приватность. Всё по желанию, по умолчанию приватно.

Критерий успеха владелец сформулировать не смог («нужно и удобно, и красиво»), поэтому опираемся на разобранное в ресёрче (раздел 12) и на утверждённые макеты. Практическая проверка: владелец и его девушка переходят на v2 и не хотят обратно; до первой карточки на телефоне не больше двух рядов элементов управления; добавить тайтл с телефона можно, ни разу не прокручивая панель.

## 3. Подпроекты и порядок

Четыре подпроекта, у каждого свой эпик в канбане и свой раздел в плане.

| Эпик | Подпроект | Что внутри | Результат |
|---|---|---|---|
| **A** | Фундамент v2 | Новое приложение в `app/` (Vite + React + TS), перенос `lib/` на TypeScript вместе с тестами, дизайн-токены и базовые компоненты, CI: сборка и деплой в `/v2/` рядом с текущей версией. Отдельно: фикс BL-26 в текущей версии. | v2 открывается по `/backlog/v2/`, показывает экран входа и пустую оболочку. Текущая версия работает как раньше. |
| **C** | Редизайн ядра на текущей схеме | Все экраны бэклога в новом дизайне поверх **нынешних** таблиц: вход, сетка, панель тайтла, редактирование, добавление (BL-25), фильтры, жанры, «Что посмотреть?», личные итоги, профиль (тема, участники, выход). Паритет со всеми функциями v1 (раздел 6.12). Переключение: v2 в корень, v1 удаляется. | Все пользуются v2, v1 и мёртвый код удалены. |
| **B** | Модель данных v2 | Слияние `overrides`/`parts` в одну таблицу `titles`, профили с ником, доски (личная + общая, BL-24), переключатель досок, приглашение в общую доску по нику, внешние ID с дозаполнением, `completed_at`. | Доски работают, данные в новой схеме, старые таблицы удалены. |
| **D** | Социальщина | Друзья (заявки, ссылка-приглашение, поиск по нику, удаление), приватность, лента, совпадения, профиль друга с совпадением вкусов, лидерборд. | Вкладка «Друзья» и соцчасть «Итогов» работают. |

**Порядок: A → C → B → D.** Это отличается от первого ответа (A → B → C → D) по одной причине: v2 переписывается на React с нуля. Если менять схему (B) до переключения на v2, придётся держать совместимость со старым клиентом или переписывать его синхронизацию, а это выброшенная работа. Поэтому сначала v2 доезжает до паритета на старой схеме и заменяет v1 (C), и только потом схема меняется под одного клиента (B). Для пользователей это тоже лучше: новый дизайн появляется раньше.

**Вне рамок** (отдельные задачи, не трогаем):
- BL-16 (обложки base64 → Supabase Storage);
- BL-17 и BL-20 (свой сервер, на hold);
- соцфункции «посоветовать», оценки, копирование с полки друга, годовые итоги;
- push-уведомления, открытая регистрация, ссылки на тайтл, вид списком, несколько общих досок.

## 4. Архитектура v2

### 4.1 Стек

| Слой | Выбор | Почему |
|---|---|---|
| UI | React 19 + TypeScript | Много состояния (панели, переключатели, лента, друзья); Motion для переходов общего элемента есть только у React; тот же стек, что у Chu-ban. |
| Сборка | Vite | Быстро, есть PWA-плагин. |
| Анимации | Motion (`motion/react`) | Пружины, `layoutId` для перехода «карточка → панель», `useReducedMotion`. |
| Стили | CSS Modules + `tokens.css` | Токены уже в CSS-переменных, темы переключаются одним атрибутом. Tailwind не нужен. |
| Иконки | `@phosphor-icons/react` | Решение 14. Один вес на всё приложение: `regular`, активные пункты `fill`. |
| Шрифты | `@fontsource/onest`, `@fontsource/unbounded` | Локально, без Google Fonts в проде. |
| Состояние | Zustand | Маленький стор поверх модулей данных, без лишних перерисовок. |
| Данные | `@supabase/supabase-js` 2 (npm, не CDN) | |
| PWA | `vite-plugin-pwa` (Workbox) | Оболочка: сначала сеть; постеры: сначала кэш (как сейчас). |
| Тесты | Vitest (логика), Playwright (e2e и скриншоты) | |

Размер: React + Motion + Supabase ≈ 150KB gzip. Для PWA с кэшем оболочки это приемлемо. Бюджет первой загрузки — 250KB gzip JS, следим в CI.

### 4.3 Параллельная жизнь v1 и v2

- GitHub Pages переключается на деплой из GitHub Actions. Workflow собирает `app/` в `dist/v2/`, кладёт рядом статические файлы v1 в `dist/` и публикует всё вместе.
- В Supabase Auth в Redirect URLs добавляется `https://ledoksi.github.io/backlog/v2/`.
- Сервис-воркер v2 регистрируется со scope `/backlog/v2/`, вложенный scope перекрывает воркер v1.
- Обе версии работают с одной базой. Пока идёт C, **схему менять нельзя** (только добавлять необязательные колонки).
- Переключение (последняя задача C): v2 собирается в корень, v1 удаляется. Новый воркер с тем же scope заменяет старый, старые кэши чистятся при активации.

### 4.4 Данные на клиенте

- Логика «локальное зеркало + очередь правок + подтягивание + realtime» из `lib/sync.js` переносится **по поведению**, с тестами:
  - очередь разбирается до чтения общего состояния;
  - при первом запуске сначала отправка, потом чтение;
  - чужая правка не перебивает открытую панель или форму: перерисовка откладывается;
  - артефактные `null` вычищаются;
  - если таблицы или колонки нет, работа деградирует мягко.
- Зеркало остаётся в `localStorage` (данных мало): ключи с префиксом `bl2:`, чтобы v1 и v2 на одном устройстве не мешали друг другу.
- Правки уходят патчем только по изменённым полям (upsert по колонкам), как сейчас.
- Индикатор синхронизации появляется только когда что-то не отправлено (как Task 49 в v1).

## 5. Дизайн

Полностью описан в [`design-system.md`](../../design/2026-09-25-redesign/design-system.md) и макетах. Здесь только то, что влияет на поведение.

- **Навигация.** Телефон: стеклянная капсула снизу (Бэклог / Друзья / Итоги / Профиль) и круглая «+» справа от неё. Десктоп (≥1024px): боковое меню 96px слева. Пока D не сделан, пункта «Друзья» нет, а колонка «У друзей» на десктопе скрыта.
- **Тема.** «Как в системе» по умолчанию, выбор в профиле. Хранится в `profiles.theme` (синхронизируется между устройствами) и дублируется в `localStorage`, чтобы первая отрисовка не мигала. До появления колонки в B — только `localStorage`.
- **Точки перелома.** До 767px — телефон; 768–1023px — две колонки сетки превращаются в 3–4, навигация остаётся нижней; от 1024px — десктоп с боковым меню, 5 колонок, правая колонка «У друзей» от 1280px.
- **Панели.** Нижние панели на телефоне; на десктопе панель тайтла — модальное окно 880px по центру, жанры — выпадающая панель у чипа «Жанры».
- **Кнопка «Назад» телефона.** Открытая панель добавляет запись в `history`, поэтому «Назад» закрывает панель, а не выходит из приложения. Своего URL у панели нет (решение 15).

## 6. Экраны и поведение

Для каждого экрана: макет → поведение → состояния (загрузка / пусто / ошибка / офлайн).

### 6.1 Вход и первый запуск — `ACSignIn`, `ACNickname`
- Вход: стена постеров, заголовок, «Войти через Google», подпись «Вход по приглашению».
- Если пришли по ссылке-приглашению (`#f/<token>`), токен сохраняется в `localStorage` до входа.
- После входа:
  - есть профиль → приложение;
  - нет профиля, но есть токен или email в `allowed_emails` → `complete_signup`, затем экран ника (раздел 7);
  - иначе экран «Этот аккаунт пока не приглашён» с кнопкой «Выйти».
- Экран ника: имя (из Google) и `@ник` с живой проверкой занятости (не чаще раза в 400мс), правила ника `^[a-z0-9_]{3,20}$`, «Продолжить». До B экрана ника нет, после входа сразу открывается приложение.

### 6.2 Бэклог — `ACGrid`, `ACDesktop`
- **Шапка:**
  1. переключатель «Моё / Общее» с аватарами участников (скрыт, если общей доски нет) и кнопка поиска (поле раскрывается на всю ширину шапки);
  2. вкладки категорий с числами;
  3. ряд чипов, прокручивается горизонтально: «Что посмотреть?», «В процессе N», «Ещё выходит», «Жанры». На десктопе справа в том же ряду «N тайтлов» и сортировка (сегменты во всплывающей панели: актуальное / добавлено / название / год).
- **Фильтры:**
  - статус — чип «В процессе» (повторное нажатие снимает);
  - полный набор статусов, «Скрыть завершённое» и сортировка на телефоне — в панели «Фильтры» (последний чип ряда с иконкой настроек и числом активных фильтров); на десктопе сортировка стоит справа в ряду, а панель «Фильтры» — всплывающая у того же чипа;
  - жанры — «любой из выбранных» (как сейчас);
  - «Только черновики» удаляется вместе с понятием черновика (решение 19).
- **Карточка:**
  - постер, плашка статуса, у сериалов с частями — прогресс «Сезон N из M» и «ждём K-й»;
  - название и мета;
  - мини-аватар друга, если у него тоже есть этот тайтл (только после D).
- **Быстрый статус:** долгое нажатие показывает три статуса над постером, на десктопе они появляются по наведению. Для тайтлов с частями вместо трёх статусов показываются «Отметить все вышедшие» и «Открыть сезоны».
- **Порядок «Актуальное сначала»:** в процессе → в бэклоге → ещё не вышло → завершено. После смены статуса карточка не прыгает, пока пользователь в сетке (отложенная пересортировка, как в v1).
- **«Что посмотреть?»:** случайный тайтл текущей вкладки, открывается его панель. В кандидаты не попадают:
  - завершённые и `unreleased`;
  - игры;
  - **(BL-26)** тайтлы с частями, у которых отмечены все вышедшие части (досмотрено всё доступное, ждём продолжения).

  На вкладке «Игры» чип неактивен с подсказкой. Если кандидатов нет, показывается «Тут всё посмотрено».
- **Состояния:**
  - загрузка — 6 скелетонов карточек;
  - пустая доска — `ACEmpty`;
  - пустой результат фильтра — «Ничего не нашлось» и «Сбросить фильтры»;
  - офлайн — работает из зеркала, в шапке маленькая плашка «Нет сети, правки сохранятся».

### 6.3 Панель тайтла — `ACSheet`
- Постер, название, оригинальное название, мета (категория, год, жанры).
- Статус: три сегмента. У тайтла с частями статус вычисляется и сегменты заменяются прогрессом «Просмотрено X из Y, впереди ещё Z».
- Сезоны и части: чекбоксы, невышедшие неактивны и с датой, «Отметить все вышедшие».
- «У друзей» (после D): чипы «Вадим завершил», «Лёша хочет»; нажатие открывает профиль друга.
- Синопсис и описание сезонов, платформы (у игр).
- Действия внизу:
  - «Редактировать»;
  - «Копировать в Моё / Общее» (после B; скрыто, если второй доски нет; при дубле показывает «Уже есть в …»);
  - «Скрыть от друзей / Показать друзьям» (после D);
  - «Удалить» с подтверждением.

### 6.4 Редактирование — `ACEdit`
- Поля:
  - обложка: загрузить фото (уменьшение на клиенте до 900px, JPEG 0.82, как Task 41) или ссылка;
  - название, оригинальное название, категория, год;
  - жанры чипами;
  - сезоны и части (название, год, вышел / не вышел, добавить / удалить, порядок перетаскиванием);
  - описание сезонов и платформы (у игр);
  - синопсис;
  - переключатель «Ещё не вышло» (у тайтлов без частей, как Task 44).
- Кнопки «Отмена / Сохранить» закреплены **вне прокрутки**. Сохраняются только изменённые поля.
- При уходе с несохранёнными изменениями спрашиваем «Отменить изменения?».

### 6.5 Добавление тайтла — `ACQuickAdd` (BL-18, BL-25)
- Сначала категория (4 сегмента, по умолчанию «Кино»), затем поле названия с автопоиском по провайдеру категории. Провайдеры как сейчас: TMDb (кино и сериалы) через CORS-прокси при блокировке, Shikimori (аниме), Steam с откатом на RAWG (игры), платформы для Steam берутся из RAWG.
- Результаты: до 5 строк с постером, названием и метой, «+» добавляет сразу. В конце кнопка «Нет нужного? Добавить “…” вручную».
- **BL-25:** панель привязана к видимой области над клавиатурой (`visualViewport`, `interactive-widget=resizes-content` в meta viewport). Поле и первые результаты видны сразу после открытия клавиатуры, прокрутка не нужна. Проверяется e2e на эмуляции iPhone с открытой клавиатурой (раздел 10).
- Дубль (тот же внешний ID, либо тот же `slug-year` до B) → «Этот тайтл уже есть в бэклоге» под полем.
- При добавлении сохраняются `source` и `source_id`. В подпроекте C в `drafts` добавляются две необязательные колонки `source`, `source_id` (это разрешено правилом 4.3: v1 их не читает и при своих частичных upsert не затирает), поэтому новые тайтлы получают внешний ID с первого дня, а дозаполнение в B касается только старых.

### 6.6 Жанры — `ACGenres`
Панель снизу (на десктопе — выпадающая у чипа): чипы жанров с числом тайтлов, мультивыбор, «Сбросить / Показать N».

### 6.7 Профиль — `ACProfile`
- Аватар (цвет от id, первая буква имени), имя, `@ник`, «Изменить».
- Доски: «Моё» (N тайтлов, видимость) и «Общее с …» (участники, «Участники»); если общей доски нет — «Создать общую доску» → пригласить по нику.
- Оформление: «Светлая / Тёмная / Как в системе».
- Строки: «Приватность», «Скрытые тайтлы N», «Пригласить в Бэклог» (ссылка, раздел 6.10).
- «Выйти из аккаунта».
- До B вместо блока досок — нынешние функции: «Пригласить по email», «Участники» (список, выйти, удалить; появляется, когда участников больше одного).

### 6.8 Итоги — `ACStats`, `ACStatsDesktop`
- Период: «Месяц / Год / Всё время».
- Главная карточка (акцентная, с веером постеров завершённого): «Сентябрь. 7 тайтлов завершено», сравнение с прошлым периодом, «Ещё N ждут новых сезонов».
- Четыре плитки по категориям: фильмы, сезоны сериалов, сезоны аниме, игры.
- «Любимые жанры» периода — чипы с числами.
- Лидерборд (после D): вкладки по категориям, до 10 мест, моя строка подсвечена; подпись «В кино считаем фильмы, в сериалах и аниме сезоны, в играх пройденные игры». Если я не участвую — плашка «Включи участие в лидерборде в приватности».
- До B дат завершения нет вообще, поэтому в C «Итоги» показывают только «всё время» (переключатель периода скрыт). После B месяц и год считаются по `completed_at`, а старые завершённые тайтлы без даты попадают только во «всё время» (раздел 7.5).

### 6.9 Приватность — `ACPrivacy` (после D; строка в профиле появляется вместе с D)
- «Кто видит доски»: у каждой доски три уровня. Для общей доски — «Менять может любой участник».
- Переключатели участия:
  - «Лидерборд» (выкл. по умолчанию);
  - «Активность в ленте» (вкл.);
  - «Совпадения» (вкл.);
  - «Поиск по нику» (вкл.).

  Переключатели действуют только в рамках видимости досок: при «Только я» ничего не видно, как бы они ни стояли.
- «Скрытые тайтлы»: список с кнопкой «Показать».

### 6.10 Друзья — `ACFriends`, `ACFriendsDesktop`, `ACFriendProfile`, `ACAddFriend` (подпроект D)
- Вкладки: «Лента / Совпадения N / Друзья N».
- Заявки сверху: в друзья («Катя хочет дружить», совпадение вкусов, «Принять / ✕») и в общую доску («Даша зовёт в общую доску», «Принять / ✕»).
- Лента: группы «Сегодня / На этой неделе / Раньше» (14 дней). Склейка:
  - отметки частей одного тайтла одним человеком за сутки → «посмотрела 2 сезона «Фрирен»»;
  - добавления одного человека в пределах часа → «добавил 12 тайтлов» с полоской постеров.

  Нажатие на событие открывает профиль друга на нужной вкладке. Кнопки «Добавить к себе» нет: копирование с полки друга владелец исключил (решение 31).
- Совпадения: «Вы с Вадимом оба хотите «Бэтмена»», «Лёша тоже ждёт Split Fiction».
- Друзья: список с процентом совпадения вкусов → профиль друга.
- Профиль друга:
  - аватар, имя, «@ник, в друзьях с …»;
  - совпадение вкусов (72%, «14 общих тайтлов», «5 хотите оба», общие жанры);
  - вкладки «Завершено / Смотрит / Хочет» с пометкой «общее»;
  - в «⋯»: «Удалить из друзей» с подтверждением.
- Добавить друга:
  - «Твоя ссылка» (7 дней, «Копировать», «Поделиться» через `navigator.share`);
  - «или найди по нику» — поиск от 2 символов, «Добавить» отправляет заявку.
- Бейдж на «Друзьях» = новые события после последнего захода + входящие заявки.

### 6.11 Мелочи, которые обязаны остаться
- Производный статус и `airingStatus` для тайтлов с частями (правила из README v1, раздел «Сезоны и части»). **Изменение:** в v2 статус вычисляется при записи и хранится (нужен серверу для ленты и лидерборда); ручной статус, выставленный до появления частей, не теряется (раздел 7.2).
- Два тайтла с одинаковым названием и разным годом — разные записи; повторное добавление того же — блокируется.
- Удаление всегда с подтверждением.

### 6.12 Паритет с v1 (чек-лист конца C)
Вкладки с числами; поиск (с задержкой); фильтры (статус, жанры, «ещё выходит», скрыть завершённое); 4 сортировки; «Что посмотреть?» с правилами BL-26; итоги; добавление с автопоиском по 4 провайдерам и CORS-прокси; редактирование всех полей, загрузка обложки, редактор частей, «Ещё не вышло»; удаление; чеклист частей и «Отметить все вышедшие»; производный статус и «Всё ещё выходит»; пригласить по email, участники, выйти, удалить, выход из аккаунта; индикатор синхронизации; офлайн-очередь; realtime; установка PWA и офлайн-оболочка; ленивая загрузка постеров; отложенная пересортировка; экран «не приглашён».

### 7.2 Правила записи
- Клиент пишет только в `titles` своих досок (RLS: `workspace_id` среди досок пользователя в `workspace_members`).
- При изменении `parts` или `checked_parts` клиент пересчитывает `status` и `airing_status` (логика `withDerivedStatus` переезжает в `lib/derive.ts`) и пишет их вместе. Если у тайтла был ручной статус, он переезжает в `manual_status` и возвращается, когда части удалены.
- Триггер `titles_status_ts`:
  - при переходе в `in_progress` ставит `started_at`, если он пуст;
  - при переходе в `done` ставит `completed_at = now()`;
  - при уходе из `done` очищает `completed_at`.
- Триггер `titles_activity` пишет `activity_events`, только если доска не `private` и тайтл не `hidden` (ещё раз проверяется при чтении):
  - `added` — на вставку;
  - `started`, `completed` — на смену статуса вперёд;
  - `parts` — на новые ключи в `checked_parts`.

  Откаты статуса назад и правки полей событий не создают.
- Ежедневная задача `pg_cron` (расширение включить) удаляет события старше 90 дней.

### 7.4 Совпадение вкусов
Считается только по видимым друг другу тайтлам без скрытых, по ключу тайтла. Нужно минимум 5 видимых тайтлов у каждого, иначе ответ «мало данных».

- `T` — косинусная похожесть множеств завершённых: `|D₁ ∩ D₂| / √(|D₁|·|D₂|)`;
- `G` — косинусная похожесть векторов жанров (завершённые + в процессе);
- `W` — похожесть «хочу»: `(|W₁ ∩ W₂| + |W₁ ∩ D₂| + |W₂ ∩ D₁|) / √(|W₁ ∪ D₁|·|W₂ ∪ D₂|)`, обрезается до 1.

Итог: `round(100 · (0.6·T + 0.3·G + 0.1·W))`. Возвращаем процент, «общих тайтлов» `|D₁ ∩ D₂|`, «хотите оба» `|W₁ ∩ W₂|` и 3 общих жанра. Подсказку «друг завершил из твоего хочу» не показываем (решение 52).

### 7.5 Лидерборд
- Участники: `in_leaderboard = true`.
- Кино и игры: число различных ключей тайтлов с `completed_at` в периоде по всем доскам пользователя; общая доска засчитывается каждому участнику, дубль в личной и общей — один раз.
- Сериалы и аниме: число отметок в `checked_parts` с датой в периоде (различные ключ + индекс части). У тайтлов без частей завершение считается за один сезон.
- Периоды: текущий месяц, текущий год, всё время. Для «всего времени» завершённые тайтлы без даты (перенесённые из v1) тоже считаются.
- Топ-10 и моё место.

### 7.6 Миграция данных (строгий порядок)
1. Резервная копия всех таблиц (выгрузка в JSON вне репозитория + бэкап Supabase).
2. Создать новые таблицы и колонки, старые не трогать.
3. Доски:
   - пространство с 2 участниками → `shared`, каждому участнику создаётся пустая `personal`;
   - пространство с 1 участником → `personal`;
   - `workspace_members` заполняется из `profiles.workspace_id`.
4. `titles` ← `drafts` + поля `overrides` поверх + `parts.indices` → `checked_parts` с датой `parts.updated_at`. Флаг `draft` отбрасывается. Статус и `manual_status` вычисляются Node-скриптом `tools/migrate-v2.ts` через ту же `lib/derive.ts`, что и в приложении.
5. Проверка: скрипт сравнивает эффективные тайтлы до и после по каждому пространству (id, статус, части, поля) и печатает расхождения. Владелец смотрит глазами в v2.
6. Переключение клиента v2 на новые таблицы (релиз).
7. Дозаполнение внешних ID: `tools/backfill-sources.ts` ищет каждый тайтл у провайдера его категории.
   - Совпали нормализованное название, год и категория, и кандидат один → записывает сразу.
   - Иначе пишет в `docs/superpowers/notes/sources-review.md` таблицу «тайтл → кандидаты», владелец отмечает выбор, повторный запуск применяет.
8. Через неделю без проблем: удалить `drafts`, `overrides`, `parts`, старый триггер и функцию.

## 8. Безопасность и приватность
- RLS на всех таблицах. Свои доски — полный доступ участникам. Чужие данные — только через RPC из 7.3.
- Профили: свой — чтение и запись; друзей и участников досок — чтение (без email); остальных — только ник, имя и цвет через `search_users`, лидерборд и полку `everyone`.
- Email никогда не отдаётся никому, кроме владельца профиля.
- По умолчанию: доски `private`, в лидерборде нет. Ничего не уходит друзьям, пока пользователь сам не открыл доску.
- Токен ссылки: 10 символов из `[a-z0-9]` (≈51 бит), срок 7 дней, погашение фиксируется.

## 9. Мёртвый код и чистка
Удаляется в конце C вместе с v1: `data.js` (160KB), `tools/migrate-catalog.js`, `lib/validate.js` в прежней роли (правила переезжают в TS-типы и `validate.ts`), UI и синхронизация `rating`, понятие «черновик» (`draft`, фильтр «Только черновики»), баги `sw.js` (кэширует `data.js`, не кэширует `lib/auth.js`) — уходят вместе с файлом, SQL-блоки в README переезжают в `supabase/migrations/`, README переписывается под v2. В коде v2 комментарии только «почему», без ссылок на номера задач.

## 10. Тестирование
- **Логика (Vitest):** все 227 тестов переносятся вместе с `lib/` и должны пройти до любых изменений поведения. Новые тесты: `derive.ts` (производный статус с `manual_status`), фильтр BL-26, форматирование строк ленты и итогов (сама склейка событий — на сервере и тестируется в SQL).
- **SQL (`supabase/tests/`):** RLS (чужие доски не читаются и не пишутся), каждая RPC приватности (`private` не утекает, `hidden` не утекает, `share_*` учитываются, email не отдаётся), лимит «одна личная + одна общая», триггеры `completed_at` и событий. Запуск на локальном Supabase (`supabase start`, `supabase test db`) или на ветке проекта.
- **e2e (Playwright):** Supabase подменяется заглушкой (как при аудите 2026-09-25: подменённый `supabase-js` с фиктивной сессией). Сценарии:
  - вход → сетка → панель → смена статуса → отметка сезона;
  - добавление через поиск с открытой клавиатурой (iPhone 13, проверка, что поле и первый результат в видимой области: BL-25);
  - редактирование и сохранение;
  - фильтры и жанры;
  - «Что посмотреть?» не выдаёт досмотренное (BL-26);
  - тема: переключение и сохранение.
- **Скриншоты:** 390×844 и 1440×900, светлая и тёмная, ключевые экраны. Сравниваются с эталоном с допуском.
- **Бюджеты в CI:** JS ≤ 250KB gzip, Lighthouse PWA и доступность ≥ 90.
