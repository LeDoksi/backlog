# Каталог как данные пространства — дизайн

Дополнение к [`2026-09-04-auth-workspaces-design.md`](2026-09-04-auth-workspaces-design.md) — читается вместе с ним, эта спека ничего в нём не переопределяет, кроме одного явно помеченного пункта ниже.

## Контекст и цель

Исходная спека (раздел «Что не меняется») утверждала: *«Каталог `data.js` остаётся общим и статичным для всех пользователей (это не персональные данные, а курируемый список тайтлов)»*. Это оказалось неверно по факту: `data.js` содержит не только «факты о тайтле» (год, жанры, синопсис), но и личный прогресс просмотра владельца прямо в поле `status` — на сегодня 67 тайтлов стоят как `'done'`, 118 как `'queue'`. Это одна и та же статичная строка кода, которая грузится одинаково у всех посетителей сайта, независимо от Supabase-аутентификации и пространства.

Из-за этого приглашённый друг в своём новом личном пространстве увидел бы все 185 тайтлов владельца, вместе с его историей просмотров — то есть «пустого» бэклога по факту не существовало бы, что напрямую противоречит требованию №2 исходной спеки («у каждого пользователя — свой приватный бэклог по умолчанию»).

**Это дополнение отменяет и заменяет** пункт исходной спеки про `data.js` из раздела «Что не меняется». Новое требование, подтверждённое владельцем: **новое пространство должно начинаться ровно с нуля тайтлов, без единой захардкоженной записи в коде.**

## Решение: каталог переезжает в `drafts`, привязанные к `workspace_id`

`drafts` — это уже одна из четырёх таблиц синхронизации, которая получает `workspace_id` в Task 2 исходного плана. Она уже почти повторяет форму тайтла (`id, title, category, status, year, genres, rating, synopsis, cover, draft`) — не хватает только полей `originalTitle`, `seasonInfo`, `platforms`, `parts`, `airingStatus`, которые уже гоняются через `EDITABLE_OVERRIDE_FIELDS` при редактировании.

Вместо отдельной таблицы под «канонический каталог» — `drafts` расширяется недостающими полями и становится **единственным источником тайтлов**. Разделения на «черновик, ожидающий попадания в канон» и «канонический тайтл» больше не существует: любая строка `drafts` твоего пространства — это и есть тайтл в твоём бэклоге, целиком, с первого дня.

Следствия:
- Новое пространство = 0 строк в `drafts` = 0 тайтлов на экране. Именно то, что требовалось.
- `data.js` перестаёт грузиться в рантайме (`<script src="data.js">` убирается из `index.html`, глобальная `TITLES` исчезает из `app.js`). Файл остаётся в истории git нетронутым — на случай, если после миграции что-то придётся сверить или откатить.
- Пополнение бэклога — **только через существующий quick-add в самом сайте** (поиск по названию, автозаполнение из внешнего API). Больше нет отдельного «попросить Claude добавить тайтл, он допишет `data.js`» — этот путь исчезает вместе с самим файлом-каталогом. Выбор подтверждён владельцем явно.

## Миграция существующих данных — гарантия «ничего не потеряется»

Наивный расчёт («185 из `data.js` + N существующих `drafts`») неверен: часть существующих `drafts`-строк владельца уже сегодня не показывается на экране — они «призраки», отфильтрованные клиентской логикой `pruneAdded`/`collidesWithExisting` (см. `lib/storage.js`, `lib/slug.js`), потому что их id когда-то совпал с тайтлом, который позже добавили в `data.js`. Эти строки физически лежат в Supabase, но никогда не рендерятся.

Поэтому миграция не оперирует числами руками. Скрипт миграции:

1. Берёт полный текущий `data.js` (185 записей) и текущее состояние `drafts`/`overrides`/`deleted_titles`/`parts` владельца из Supabase.
2. Прогоняет их через **ту же самую существующую логику** склейки и фильтрации, которую сегодня использует браузер для рендера (`combineWithAdded`, `applyOverlay`, `pruneAdded`, `withDerivedStatus` из `lib/storage.js`) — не переписанную копию этой логики, а вызов тех же функций.
3. Результат — ровно тот список тайтлов (со всеми эффективными полями: статус после применения overrides, `parts`, всё), который сегодня реально виден в браузере владельца. Именно этот список построчно становится новым содержимым `drafts` для его `workspace_id`.
4. «Призрачные» строки, отфильтрованные на шаге 2, в новую таблицу не попадают — они и так были мёртвым весом, никогда не отображались.
5. Перед тем как выключать старый код (`data.js`, старые `overrides`/`deleted_titles` в их прежней роли), владелец **глазами** сверяет в браузере, что после миграции ничего не пропало и не задвоилось. Только после этого — переключение рендера на новый источник и удаление старого пути.

`data.js` как файл не удаляется из репозитория — просто перестаёт быть частью рантайма.

## Что отменяется как более не нужное

- **Таблица `deleted_titles`.** Она существовала только чтобы скрыть тайтл из общего `data.js`, не имея возможности удалить чужую/общую строку кода. Когда каталог — это твои собственные строки в `drafts`, «удалить тайтл» и «удалить черновик» — одно и то же действие: убрать свою строку. Отдельный тумбстоун-механизм отмирает.
- **Эвристика коллизий по префиксу+году** (`lib/slug.js`: `collidesWithExisting`, `isSupersededBy`, часть `uniqueId`). Она решала проблему двух независимых источников id (статичный файл + таблица), которые могли случайно совпасть по формату. При одном источнике достаточно обычной проверки на существование id.

**Что при этом обязано сохраниться** (проверено с владельцем явно): два тайтла с одинаковым названием, но разным годом (например, два разных «Шаман Кинг» — 2001 и новый ремейк) обязаны получать разные id и добавляться независимо. Это гарантируется самой схемой id (`slug-year` из `lib/slug.js`’s `makeId`) без какой-либо специальной логики — разные годы дают разные id естественным образом. А вот повторная попытка добавить **тот же самый** тайтл (тот же slug и год) — даже если существующую запись уже отредактировали (дописали сезоны, поменяли рейтинг) — должна блокироваться обычной проверкой «такой id уже есть в этом пространстве»: id не меняется при редактировании, редактирование идёт по полям той же строки, так что повторный id всё равно совпадёт и будет пойман.

## Что не меняется (кроме отменённого выше пункта исходной спеки)

- Модель `workspace` как владельца данных, RLS через `current_workspace_id()`, приглашение/выход/удаление участника — всё из исходной спеки без изменений.
- `lib/sync.js`: аутбокс, слияние при пуле, realtime — работает с расширенным `drafts` ровно так же, как с прежним; меняется только состав полей (`DRAFT_FIELDS` пополняется), не сам механизм.
- Обложки (`images/covers/*.jpg`) остаются статичными файлами в репозитории — переезжают только метаданные (текст, статус, жанры и т.д.), не картинки.

## Границы (что решаем отдельно, не здесь)

- `tools/validate-data.js` (валидатор `data.js` при коммите) теряет свой прежний смысл — решение, выкинуть его или переиспользовать для клиентской проверки формы данных, принимается на этапе плана реализации, не здесь.
- Переписывание раздела README «Как добавить новый тайтл» под чисто quick-add воркфлоу — задача уровня плана реализации.
