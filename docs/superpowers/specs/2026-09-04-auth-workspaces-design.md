# Аутентификация и общие пространства — дизайн

## Контекст и цель

Сейчас «Бэклог» — статический сайт с одним общим Supabase-состоянием: все четыре таблицы синхронизации (`overrides`, `deleted_titles`, `drafts`, `parts`) открыты кому угодно, кто знает URL проекта (`using(true) with check(true)` на всех RLS-политиках), доступ к анонимному ключу — единственный барьер. Каталог (`data.js`) статичен и общий для всех, редактируется только через Claude.

Владелец хочет пустить пользоваться сайтом друга, у которого должен быть **свой отдельный, приватный от владельца бэклог**. При этом с девушкой владелец продолжает пользоваться **одним общим** бэклогом — как сейчас, просто под настоящими раздельными логинами вместо анонимного доступа.

Три требования, подтверждённые в диалоге:
1. Вход через Google-аккаунт.
2. У каждого пользователя — свой приватный бэклог по умолчанию.
3. Возможность объединять бэклоги нескольких аккаунтов в одно общее пространство (сейчас — владелец + девушка).

## Модель: workspace как единица владения данными

Данные принадлежат не пользователю, а **пространству** (`workspace`), в котором пользователь состоит. У пользователя всегда ровно одно пространство. Если пространство состоит из одного человека — это его личный приватный бэклог. Если из нескольких — это то самое «общее» между ними.

Это позволяет всей текущей архитектуре синхронизации (аутбокс, слияние при пуле, дедупликация артефактных `null`, realtime-подписка) остаться ровно такой же — просто данные теперь скоуплены по `workspace_id`, а не общие на всех.

### Новые таблицы

```sql
create table workspaces (
  id uuid primary key default gen_random_uuid(),
  created_at timestamptz not null default now()
);

create table profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  email text not null,
  workspace_id uuid not null references workspaces(id),
  created_at timestamptz not null default now()
);

create table allowed_emails (
  email text primary key,
  invited_by uuid references auth.users(id),
  workspace_id uuid references workspaces(id), -- если задан: сразу в это пространство при первом входе
  created_at timestamptz not null default now()
);
```

### Изменения в существующих таблицах

`overrides`, `deleted_titles`, `drafts`, `parts` получают колонку `workspace_id uuid not null references workspaces(id)`.

RLS на этих четырёх таблицах меняется с «разрешено всем» на:

```sql
using (workspace_id = (select workspace_id from profiles where id = auth.uid()))
with check (workspace_id = (select workspace_id from profiles where id = auth.uid()))
```

### Создание профиля при первом входе

Postgres-триггер на `auth.users` (после insert):
1. Если `email` нет в `allowed_emails` — вход не создаёт `profiles`-строку (см. «Экран входа» ниже — без `profiles` пользователь ничего не видит и не пишет, RLS блокирует всё).
2. Если есть, и `allowed_emails.workspace_id` задан — новая `profiles`-строка с этим `workspace_id`.
3. Если есть, и `workspace_id` не задан — создаётся новая `workspaces`-строка, `profiles.workspace_id` указывает на неё (личное пространство).

Это стандартный паттерн Supabase (`handle_new_user`-триггер), без отдельной серверной функции.

## Экран входа

Приложение до входа не показывает бэклог вообще — отдельный экран в текущей тёмной стилистике: логотип/название + кнопка «Войти через Google».

После входа через Supabase Auth (`signInWithOAuth({provider:'google'})`):
- Если для этого email создался `profiles` (см. триггер выше) — пускаем в приложение как обычно.
- Если нет (email не был в `allowed_emails`) — спокойный экран «Этот аккаунт пока не приглашён», без деталей и без пугающих формулировок. Возможность выйти и попробовать другой Google-аккаунт.

RLS дублирует эту проверку на уровне базы — даже если кто-то обойдёт клиентский экран, без `profiles`-строки читать/писать нечего.

## Приглашение

Кнопка в топбаре (рядом с индикатором синхронизации) открывает небольшую форму:
- Поле email.
- Чекбокс **«Добавить в моё пространство»**, по умолчанию **выключен**.

Отправка вставляет (или обновляет, если email уже был приглашён раньше — `upsert`) строку в `allowed_emails`:
- `email` = введённый,
- `invited_by` = `auth.uid()` пригласившего,
- `workspace_id` = `workspace_id` пригласившего, если чекбокс включён, иначе `null`.

RLS на `allowed_emails` разрешает `insert`/`update` любому аутентифицированному пользователю (см. «Модель безопасности» ниже) с `check (invited_by = auth.uid())` — пригласивший не может подставить чужой `invited_by`.

**Приглашение уже существующего пользователя.** Триггер на `auth.users` (создание `profiles`) срабатывает только при первом входе конкретного Google-аккаунта — то есть строка `allowed_emails` сама по себе применяется только к ещё не заходившим. Если приглашаемый email уже когда-то входил (у него уже есть `profiles`), а чекбокс «Добавить в моё пространство» включён — нужно применить смену пространства сразу, а не ждать несуществующего повторного «первого входа». Поэтому вставка в `allowed_emails` оборачивается в RPC-функцию (а не голый insert из клиента), которая:
1. Пишет/обновляет строку `allowed_emails`, как описано выше.
2. Если чекбокс включён **и** для этого email уже существует `profiles` — сразу обновляет её `workspace_id` на пространство пригласившего (то же самое действие, что делает переключение пространства при удалении/выходе, просто в обратную сторону — присоединение, а не уход).

Так же закрывается случай «человек вышел из общего пространства, потом хочет вернуться» — по сути это то же самое повторное приглашение с отмеченным чекбоксом.

## Удаление участника и выход из пространства

Оба действия — один и тот же переход: у пользователя создаётся **новая пустая personal `workspaces`-строка**, и его `profiles.workspace_id` переключается на неё. Доступ к сайту (`allowed_emails`) не трогается ни в каком случае — это отдельное, никак не связанное действие.

**Кто может удалить кого:** любой текущий участник пространства может вывести любого другого участника этого же пространства (симметрично с правом приглашать — см. «Модель безопасности»).

**Ограничение на выход/удаление:** действие доступно только если в пространстве **больше одного участника**. Если пользователь и так один в своём пространстве — кнопки «Выйти» нет: выходить некуда, а плодить пустые пространства незачем. Это ограничение проверяется и на клиенте (не показывать кнопку), и в базе (RLS/проверка перед свитчем).

Данные (`overrides`/`drafts`/`parts`), написанные до выхода, остаются в старом `workspace_id` — у пространства, откуда человека вывели. Ничего не переносится и не удаляется. Если этот человек позже снова присоединится к этому же пространству — начнёт видеть общие данные заново (они никуда не делись), но его новое личное пространство, в котором он был между выходом и повторным присоединением, остаётся как есть (осиротевшее, но не мешающее).

## Модель безопасности

Явно выбрано, а не default по умолчанию: **приглашать и выводить участников может любой аутентифицированный пользователь**, без роли «владелец»/админ. Для круга из 2-3 доверенных людей это осознанно принятый компромисс: цепочка «приглашённый может пригласить ещё» технически возможна, но контролируема — весь список того, кто вообще может войти, всегда виден и правится в одном месте.

**Мониторинг.** Специального экрана в приложении не строится. `allowed_emails` — обычная таблица в Supabase; она смотрится напрямую в **Table Editor** дашборда (там же, где ранее выполнялись SQL-миграции) — всегда точный список без лишнего кода. Панель управления участниками пространства (нужна для функции удаления, см. выше) попутно показывает список участников текущего пространства — не полный `allowed_emails`, а именно «кто сейчас в этой группе».

## Миграция существующих данных

Текущие данные в `overrides`/`deleted_titles`/`drafts`/`parts` принадлежат владельцу и его девушке (единственным двум реальным пользователям сайта на сегодня). План миграции:

1. Создать одну `workspaces`-строку («основное» пространство).
2. Проставить всем существующим строкам всех четырёх таблиц этот `workspace_id`.
3. Предзаполнить `allowed_emails` двумя email (владелец и девушка), у обоих `workspace_id` = это основное пространство — так оба при первом входе через Google сразу окажутся в общем пространстве с уже существующими данными, без единой потери.
4. Друг при приглашении получает запись в `allowed_emails` без `workspace_id` (чекбокс не отмечен) — при первом входе получает пустое личное пространство.

## Что не меняется

- Вся логика в `lib/sync.js` — аутбокс, слияние при пуле вместо перезаписи, скраб артефактных `null`, realtime-подписка, деградация при отсутствующей таблице/колонке. Она работает с уже авторизованным Supabase-клиентом ровно как раньше с анонимным — RLS делает изоляцию прозрачной для этого слоя.
- Каталог `data.js` остаётся общим и статичным для всех пользователей (это не персональные данные, а курируемый список тайтлов).
- PWA/офлайн-режим, service worker, вся остальная функциональность приложения.

## Явно вне рамок этой задачи

- Открытая самостоятельная регистрация (см. подтверждённое решение: доступ только по приглашению).
- Роли/иерархия внутри пространства («владелец» с особыми правами) — не нужна при текущей симметричной модели.
- Наследование данных при повторном присоединении к пространству, из которого вышел.
- Переименование пространств или любой другой UI сверх необходимого (кнопка приглашения, список участников, кнопки выйти/удалить).

## Примечание к реализации (не часть дизайна, для будущего плана)

Владелец ранее просил на других проектах: сначала спроектировать и проверить весь UI, реальный auth-гейт подключать последним шагом. Для этой задачи это означает: экран входа, форму приглашения и панель участников можно построить и провизуально проверить против тестовой/подставной сессии, и только в конце подключить настоящий `signInWithOAuth`. Это будет учтено при написании плана реализации.
